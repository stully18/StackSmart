# AI database security and scaling review

## Changes in this task

`005_unlimited_ai_plan_generations.sql` removes the daily slot constraints and changes the provider default to OpenRouter. UUID remains the generation identity. The nullable legacy `generation_number` column is retained for rollback compatibility and can be removed in a later migration after old deployments are retired.

The migration preserves existing rows, foreign keys, RLS, and history. It explicitly revokes table privileges from PUBLIC, anon, and authenticated; only the backend service role can manage generation rows. The API derives user identity from the verified bearer token, never the request body. Status queries filter by that identity and return an exact count plus one metadata row, rather than all results or financial payloads. The partial `(user_id, generated_on, created_at desc)` index supports this query.

New generation records store operational metadata only. They do not copy financial inputs or generated advice into audit JSON columns. Saved plans in `financial_data` remain the canonical user-requested saved documents. Failed generations retain a safe error category without exception details or financial data. Existing historical payloads are preserved, pending an explicit retention decision. Database I/O in the affected async audit functions runs in the thread pool.

Planning storage and stock-screen reads use a dedicated five-second PostgREST timeout with client retries disabled. The provider uses five-second connect and sixty-second read timeouts without retrying the generation. ETF presentation reads existing in-memory quote cache only, then uses clearly labelled illustrative values if missing; it never starts an additional Yahoo download after the AI call. These bounds leave room for audit writes beneath the frontend's 120-second request window in normal operation.

The planning-specific nested loan schema rejects non-finite or excessive amounts, more than fifty loans, and long names. A scoped validation error response also rejects overflowing JSON numbers without echoing financial input or failing while serializing infinity. Goal constraints require defensive allocations for preservation/income/debt goals as well as risk and time-horizon constraints; the rule-based fallback applies the same policy.

Apply the migration before enabling the new backend. It is compatible with the existing backend column shape; the old backend will still impose its own limits until replaced. The new unlimited backend requires the constraint removal. Do not run all old migrations again after this migration: migration 004 would restore the quota constraints.

## Findings and next improvements

1. **Verify live state before launch.** Repository migrations and documentation are not proof of the deployed schema. Check `pg_policies`, `information_schema.role_table_grants`, constraints, function grants, and indexes for the actual project. The current Supabase MCP failed discovery and the local CLI lacked authentication; no live DDL was applied during this implementation. Root verification notes cover local migration execution and available authenticated REST probes.
2. **Keep profile data canonical.** `users_public` is the intended public profile table; older setup instructions also describe a separate `profiles` table. Inspect whether both exist and which the application uses before consolidating. Do not drop either based only on documentation. Avoid synchronizing the same mutable financial facts into profiles, plans, and generation audit rows.
3. **Normalize mutable entities; keep plan snapshots as documents.** `user_loans` already has one row per loan with an owner FK and stable UUID. Use the same approach for persisted holdings and spending goals when CRUD/history is needed: one owned row per holding/goal, constrained numeric amounts, indexed owner FK, and SELECT/INSERT/UPDATE/DELETE policies with both USING and WITH CHECK. This task only submits these as bounded request arrays; it does not create redundant persistence tables prematurely. A saved plan JSON is a historical snapshot rather than a second editable source of truth.
4. **Set audit retention deliberately.** Unlimited generation means unlimited audit growth unless retention is managed. Choose a short operational retention interval, a scheduled cleanup job for finalized audit records, and a stale-pending reconciliation policy. Preserve saved plans independently. Do not retain raw financial prompts in generic application logs or analytics.
5. **Avoid redundant indexes.** A unique constraint already creates an index. The original schema duplicates indexes on some unique/date keys (for example the Stock of the Day pick date). Inspect query plans and dependencies before removing duplicates; keep the new partial audit index because it serves a specific bounded endpoint query. Add cursor pagination to saved-plan/history endpoints before volume grows, rather than fetching entire user history.
6. **Separate Plaid items from account metadata.** Original `plaid_accounts` stores one token alongside a row constrained by `(user_id, plaid_item_id)`, even though one item can expose several accounts. A future migration should use a backend-only item/token table and an owned account table with an item FK. Verify ownership in every backend query because service-role access bypasses RLS.
7. **Correct encryption assumptions before storing live bank credentials.** The original SQL declares `plaid_access_token TEXT` with a comment to encrypt it. A comment does not implement column encryption, and platform encryption at rest does not prevent authorized SQL reads. Existing database documentation incorrectly describes automatic column encryption. Verify the actual token storage path; use a deliberate application encryption or secret-management design and keep tokens out of client-readable tables. This task does not alter Plaid behavior.
8. **Review public functions and provider payload caches.** Restrict EXECUTE on privileged functions; prefer SECURITY INVOKER, explicit owner checks, and fixed search paths. Keep raw provider cache tables backend-only; provider responses can contain more data than the public application needs. Preserve the existing market-cache lockdown migration.
9. **Re-enable abuse controls before public launch.** User-requested unlimited testing removes generation quotas but does not remove authentication. Before onboarding real users, add a deliberate abuse/cost policy, bounded concurrent jobs, retry/backpressure behavior, monitoring, and provider/privacy eligibility review. OpenRouter free-route provider limits still apply. The selected free model is for synthetic testing under its published terms; do not treat testing readiness as production privacy readiness.

## Security verification expectations

Test anon and authenticated roles for no generation-table CRUD privileges, service-role inserts beyond ten generations, preservation of history, and migration idempotency. Test one user cannot obtain another user's generation metadata through the API. A broader launch audit should separately test saved plans, profiles, loan RPCs, and Plaid ownership with two distinct users; this task's focused verification does not certify the entire application.
